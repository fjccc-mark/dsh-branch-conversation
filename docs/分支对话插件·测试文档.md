## 1. 怎么跑

```sh
npm install --legacy-peer-deps         # 官方 SDK 的 peer 声明在 npm 下需要这个开关
npm run typecheck                      # host + client 两个 program
npm run build                          # tsdown（host ESM + client CJS）+ 套加载器外壳 + 内嵌 panel.css
npm run smoke                          # 六套冒烟，一条命令跑完（82 项）
npm run layout-check                   # 画布形态量测（无头 Chromium，五档 × 展开/折叠两态）
npm run layout-shots                   # 同上，另存两态验收截图
```

单套跑法（便于定位）：

```sh
node tools/smoke/branch-smoke.mjs      # M0：存储与路由契约（14 项）
node tools/smoke/branch-m1-cases.mjs   # M1：建子会话 / 节点派生 / 孤儿升根（17 项）
node tools/smoke/branch-m4-cases.mjs   # M4：失败恢复四场景 + 文件节点 + 导出路由（15 项）
node tools/smoke/client-bundle.mjs     # M2：浏览器半产物形状、座位注册、**样式投递**（11 项）
node tools/smoke/tree-layout.mjs       # M6：**画布布局纯函数**（坐标/边/端点/重叠，15 项）
node tools/smoke/export.mjs            # M4：三种导出纯函数（13 项）
node tools/smoke/layout-check.mjs      # 形态：五档布局宽 × 两态实量（需要本机有 Chromium）
```

测试形态说明：本插件**不依赖真机 DSH** 也能覆盖主链路——
`src/testing/fake-sessions.ts` 按官方契约造了一套假会话面（`inspect` 返回 `{meta, events}`、
`list` 带 `parentSessionId`/`origin`、`agents.create` 建出的会话会落盘、`sessions.create` 建出的**不落盘**），
用它驱动**真实的** `BranchService`、`TreeStore` 与 `/branch/*` 路由；浏览器半则在一个最小
`window.__ModuleLoader__` + 模块表环境里**真实加载产物**；
页面排版则在无头 Chromium 里**用真实布局函数与真实样式表**渲染后量测。

### 5.2 画布布局（`tree-layout.mjs`，20/20；**2026-10-16 整体重写 + 补主轴用例**）

> 旧的 9 项是"轨道/缩进"口径（`├─`/`└─`/轨道压缩），**随 M6 一并作废**。
> 现在的断言全部落在**几何**上：坐标、边、端点、矩形互斥，外加"主轴串接"的 5 条语义用例。

| # | 用例 | 断言要点 |
| --- | --- | --- |
| 1 | 导出可用 | `layoutTree`、`isSessionNode` 是函数；`NODE_W=208`/`NODE_H=62`（布局常量已从客户端入口导出） |
| 2 | 空树 / null | `nodes=[]`、`edges=[]`、`size=48×48`（仅内边距）、不崩 |
| 3 | `hasOrphans` | 无孤儿为 false；任意节点 `orphan` 为 true → 面板显示「处理孤儿」入口（含被折叠隐藏的孤儿） |
| 4 | 二维坐标（同级成行） | `x = 24 + depth×264` 且只由 `depth` 决定（同深度 `x` 相同）；`y` 随槽位递增 |
| 5 | 父节点居中 | 父框 `y` = 其**首个子节点与末个子节点** `y` 的中点（深子树下"子树最上/最下叶子中点"是另一个值，这里显式区分） |
| 6 | 边数 = 可见父子关系数 | `edges` 的 `from/to` 集合与"未折叠节点的可见子节点"集合完全一致 |
| 7 | 端点贴框 | 每条边 `x1=父框右缘`、`y1=父框中线`、`x2=子框左缘`、`y2=子框中线`；`path` 的首末坐标与之一致 |
| 8 | `axis` 分类 | 父子同 `sessionId` → `main`（轴线）；跨会话（子对话 / 文件节点）→ `branch` |
| 9 | 框不重叠 | 任意两框矩形互斥；每个框都是 `NODE_W × NODE_H` |
| 10 | 折叠 = 图形行为（F-4） | 后代不进 `nodes`、**通往它们的边也不进 `edges`**、`hiddenTotal` 等于被隐藏的节点数、**剩余节点重新排布** |
| 11 | 文件节点 | `kind`/`filePath`/`fileMissing`/`turn=null`；`isSessionNode` 为 false |
| 12 | 孤儿与当前节点 | `orphan`/`current` 标记正确传递；孤儿不可跳会话 |
| 13 | 损坏数据 | 悬空子节点被忽略；有环时每个节点只出现一次、不死循环、**不多画 `b→a` 的回边**（画出来的线 = 排布期建立的父子关系） |
| 14 | 多根（升根后） | 每个根都从 `depth 0` 开始，占独立槽段、互不重叠 |
| 15 | 深链不破版 | 12 层链不截断：12 个框、11 条边、`size.width` 与最深层 `x` 严格等于公式值（深树靠画布双向滚动 + 缩放，不再靠压缩轨道） |
| 16 | **主轴串接** | 同一父节点下、同一会话的**平铺**第 1/2/3 轮 → `r→n1`、`n1→n2`、`n2→n3`；只有 `r→n1` 是真连接，后两条 `synthetic: true`；三个轮次**同深度、同列、自上而下**（主轴是纵向的），画布只占一层宽 |
| 17 | **折叠主轴的中间一轮** | 折叠第 2 轮 → 第 3 轮（它的下游）**一起消失**、通往它的线也消失、`hiddenTotal` 计入；**不能**让第 3 轮变成兄弟"越级上前" |
| 18 | **只串同一会话** | 跨会话的兄弟（子对话 / 文件节点）各自挂在真父节点上、画成 `branch` 虚线；无轮次的兄弟不参与主轴 |
| 19 | **轮次不连续不串** | 第 1、3 轮（缺第 2 轮）各自挂真父节点，**不硬接**一条主轴；不该出现合成边 |
| 20 | **真父子优先** | 真父子且同会话 + 轮次连续（如子对话里 `第2轮 → 第3轮`）→ **保持真层级**、`synthetic !== true`；跨会话那一段仍是虚线 |

### 6.5 真机轮次二：路由阻塞点已解决 + 5 个新真机 bug（2026-10-15，按 [测试计划](分支对话插件·测试计划.md) 执行）

#### 6.5.1 结论一句话

**§6.3 的阻塞点找到根因并修复**：插件把 host 路由前缀注册成 `'branch'`，
而 webserver 的前缀匹配要求**带前导斜杠**（`pathname !== prefix && !pathname.startsWith(prefix + '/')`），

#### 6.5.3 根因取证：前导斜杠对照实验

在探针插件里用**同一条** webServer 注册两种前缀，其余条件完全相同：

| 注册的 `path` | 前缀表里的键 | `ws.match('/x')` | `GET /x` | `GET /x/y` |
| --- | --- | --- | --- | --- |
| `'nolead'`（旧写法，同本插件） | `nolead` | `undefined` | **404**（落到 fallback） | **404** |
| `'/lead'`（正确写法，同官方 client-modules 的 `'/plugins'`） | `/lead` | 命中 | **200** | **200** |

官方 `@deepseek-ai/dsh-host-webserver` 的 `match()`（`lib/index.js:322-332`）：

```js
match(pathname) {
  const exact = this.exact.get(pathname)
  if (exact !== void 0) return exact
  let best
  for (const [prefix, route] of this.prefixes) {
    if (pathname !== prefix && !pathname.startsWith(`${prefix}/`)) continue   // ← 无前导斜杠的键永不命中
    if (best === void 0 || prefix.length > best.path.length) best = route
  }
  return best
}
```

**修法**：`src/core/types.ts` 的 `BRANCH_ROUTE_PREFIX` 改为 `'/branch'`；`cordis.patch.yml` 与冒烟断言同步。
回归用例已进 `branch-smoke.mjs`（断言注册的 `path === '/branch'`）。

### 6.6 页面形态量测轮（2026-10-15，网页端自动量测）

**动机**：测试计划把"窄屏不退化"（`F-5` / `W-9.1`）列为**人工拖窗口看三张截图**。
上一轮还发现"原计划的无头 Chrome 截图被平台沙箱拒绝"，也就是说这条基线当时**没有任何自动兜底**。
本轮把它做成可重复的量测，顺带抓出 4 个真缺陷。

#### 6.6.1 怎么做的（工具链）

| 组件 | 职责 |
| --- | --- |
| `tools/build/panel-preview.mjs` | 用**产物里的真 `layoutTree`** 算出流程图行，再按 `panel.css` 的同一套类名拼出与 `panel.tsx` **同构**的静态页面；生成 360/480/768/1280/1920 五档夹具 |
| `tools/smoke/layout-check.mjs` | 起一个只服务夹具的**本机回环** HTTP 服务；用无头 Chromium 打开每一档；页面把几何事实 `POST` 回服务；逐项断言；跑完按 PID 收掉自己拉起的浏览器 |

两个环境事实（都不是"猜"的，是实测出来的，已写进工具注释）：

1. **Windows 上 Chromium 的窗口有约 500px 最小宽度**：`--window-size=360,900` 实测 `innerWidth=518`
   （换 `--headless=old`、加 `--window-position` 都一样）。所以窄屏不是"把窗口开窄"，
   而是**把页面塞进一个固定宽度的裁剪容器**（`?w=360`），再用 `transform: scale()` 缩小观感
   （transform 不影响任何几何量测）。
2. **Chromium 在本机既不写管道、也不写继承的文件句柄**：`--dump-dom` 读回来永远是 0 字节
   （`stdio:'pipe'` 直接 `EPERM`）。因此量测值走"页面 `POST` 回本机服务"这条通道，
   浏览器进程只负责渲染。另外必须 `detached: true`，否则连 `--screenshot` 都不落盘。

#### 6.6.2 断言与结果（**42/42 通过**；⚠️ 这批是**旧"缩进列表"形态**的断言，已被 §6.7 取代）

| --- | --- | --- |
| 1 | 布局宽 = 目标宽（±1.5px） | 自证量测前提成立（裁剪容器真的生效了） |
| 2 | 文档无横向溢出 | `scrollWidth ≤ clientWidth + 1` |
| 3 | 流程图有轴线/分叉轨道 | 每个"非根行"都含 `│├└─` 之一（防退化成纯文字列表） |
| 4 | 节点行都在可视区内 | 每行 `getBoundingClientRect()` 不越出视口 |
| 5 | 折叠三角与「＋」都在容器内 | 行首两个按钮的盒都不越出视口（能点到） |
| 6 | **每个节点行都不宽过树容器** | `row.scrollWidth ≤ tree.clientWidth + 2` |
| 7 | 面板自身无横向溢出 | `page.scrollWidth ≤ page.clientWidth + 1` |
| 8 | 内容留在面板内滚动 | 根元素 `scrollHeight ≤ 视口高 + 1`（没让窗口整体滚） |

#### 6.6.3 本轮抓到的 4 个真缺陷（全部已修 + 有回归用例）

| # | 现象 | 根因 | 修法 | 回归用例 |
| --- | --- | --- | --- | --- |
| 14 | **`panel.css` 从未到过浏览器**：真机上页面一直是裸样式 | 浏览器半产物是 `__ModuleLoader__.load({id, factory})`，加载器只取模块**导出**，不处理任何 CSS 副作用；`src/` 里没有任何地方 import 它 | 构建时 `wrap-client-bundle.mjs` 把 `panel.css` 内嵌为 `window.__DSH_BRANCH_CSS__`；新增 `src/client/style.ts`，`apply()` 时插成 `<style data-dsh-branch-style>`（幂等） | `client-bundle.mjs` 3 项 |
| 15 | 窄屏整页横向溢出（360px 布局宽实测 **116px**） | 节点行宽由内容决定 → 行内标题 `max-width: 100%` 变成循环依赖 → 浏览器退回文字固有宽度；页面各子块没有 `min-width: 0` | 行改 `width: 100%`；`.dsh-branch-page > *` 一律 `min-width: 0` + `overflow-x: hidden`；页面只允许纵向滚动 | `layout-check` 第 2/7 项 |
| 16 | 深树 10 层的轨道前缀本身 **356px**，光缩进就宽过 360px 中央列 | `layoutTree` 每级都铺一个 3 字符轨道，深度不设上限 | 轨道压缩：超过 4 级只画 `⋯ ` + 末 4 级（末级分支符号一定保留） | `tree-layout.mjs` 1 项 |
| 17 | 极窄容器里徽标/长标题把折叠三角与「＋」挤出容器 | 没有容器级适配：辅助信息与操作入口抢同一行宽度 | `container-type: inline-size` + `@container`：≤560px 隐去徽标、≤380px 收紧间距与按钮内边距（按钮仍 ≥14px 见方）；树容器 `overflow-x: auto` 兜底 | `layout-check` 第 5/6 项 |

顺带修掉两个**只在工具里**出现的问题（也写进了注释，避免下一个人再踩）：

- **幂等判据过宽**：包装脚本原来用"正文里有没有 `__ModuleLoader__.load`"判断是否已包装，
  而 `style.ts` 的注释里恰好有这串字，导致**新产物被误判为"已包装"并跳过**——
  样式常量因此没进产物，差一点带着缺陷过测（`client-bundle.mjs` 的新断言会失败）。
  改为只认**外壳特征**（文件头是 `window.__DSH_BRANCH_CSS__ = …;\nwindow.__ModuleLoader__.load({`）。
- **假 `window` 只当函数形参**：产物读的是全局 `window.__DSH_BRANCH_CSS__`，
  而测试原来把假 `window` 只作为 `new Function('window', …)` 的形参传入，于是断言看到的是 `undefined`。
  改为把假 `window` 挂到 `globalThis` 上（与 `tree-layout.mjs`、`src/client/style.ts` 的取值口径一致）。

#### 6.7.2 本轮踩到的三个"环境 / 工具"坑（都已修，值得记住）

**坑 A：无头 Chromium 一度完全起不来。** 本轮前半段，父代理与子代理**各自独立复现**了同一现象：

| 试法 | 结果 |
| --- | --- |
| `msedge.exe --version` | **无任何输出**（连版本都打不出来） |
| `--headless=new --screenshot=<文件> <url>` | 进程 `exited=True code=0`，但**截图不落盘**、页面从未加载（本机回环服务收不到任何 GET） |
| `--headless=old` / `--single-process` / `--disable-crash-reporter` / `--dump-dom` | 全都不产出任何东西 |
| stderr | 只有 crashpad `OpenProcess: 拒绝访问 (0x5)` |
| 把 `stdio` 改成 `'pipe'` | 直接 `spawn EPERM`（沙箱对管道的既有边界） |

**后来同一台机器上量测又能跑了**（`layout-check` 88/88、CDP 截图也成），说明这是**环境状态**而非脚本缺陷。
处置：工具遇到"浏览器起得来但页面不渲染"时**打印可读的跳过说明 + "0 项断言执行"**，
`process.exitCode = 0`，**绝不伪装成通过**；只有"跑了几套之后才开始失败"才当真 bug 抛错。

**坑 B：`--screenshot=<png>` 在本机永远不落盘。** 各种 headless 模式、带不带 `--virtual-time-budget`、
连 `data:` 裸页面都试过——一律"进程 exit 0、png 不存在"。**但同一台机器上"页面 POST 回本机服务"
这条通道是通的**（88 条断言因此全绿），即**渲染没问题，是 `--screenshot` 这条路不通**。
改用 **DevTools 协议**：`--remote-debugging-port` + `/json/version` 拿 `webSocketDebuggerUrl` +
`Target.createTarget`/`attachToTarget(flatten)` + `Page.captureScreenshot`
（用 Node 内置 `WebSocket`，**不引任何新依赖**），实测能出图。

**坑 C（最阴的一个）：截图落盘成功 ≠ 内容对。** 把截图阶段放在 `server.close()` **之后**跑，
10 张图全是 Edge 的 `ERR_CONNECTION_REFUSED` **错误页**——文件非空、尺寸正常、**断言一条都不会红**，
只有人眼看图才发现。修法：截图必须写在**夹具服务还活着的 `try` 里**，并且**拍完一定要人眼过一遍**。
（同类教训：本仓库早先还有"预览页能看、真机没样式"——都是"看起来成功了"的假象。）

**顺带修掉的两个工具缺陷**：① 截图的 detached 浏览器句柄**不一定会 `close`**，导致 `--shots`
永远挂住（以 "unsettled top-level await" 收场），已加退出等待上限；
② `captureScreenshot` 的 `captureBeyondViewport` 在 `--headless=new` 下不保证整页，
已改成"先量文档高度、把视口调成整页高再截"。

## 10. P0-A 人工交互轮：缺陷 27 = 建子会话的通道错了（2026-10-17）

### 10.1 现象与根因

管理者在真机上点「＋」建子会话，得到两个症状：① 子会话**挂不到父会话上**；② 打开子会话后它在画布上**被当成新根**。

根因是**官方契约**（实时 inspection 的原文，不是猜的）：`sessions` 服务写着
*"Persistence is intentionally not implemented here — the agent lifecycle attaches a session-log writer
to each published session's write handle; **a session published outside that lifecycle persists nothing**"*，
而 `sessions.create()` 不给 id 时铸的是 `session-<n>` **计数器号**。旧实现走的正是这条路：

| 事实（真机存储取证） | 后果 |
| --- | --- |
| 树文档里躺着 `sessionId: "session-1"` 的节点 | 它永远匹配不到真实会话（`session-1` 不是任何已落盘会话） |
| 子会话不在 `$DSH_HOME/sessions/…`、也不在 `sessionController.list()` | 侧边栏看不到/打不开；重启即失效 |
| 打开真实子会话时 `resolveTreeId()` 找不到它 | `adopt` 只好建**一棵新树** → "被当成新根" |
| 第二个独立缺陷：挂载点取 `nodeOfSession()`（该会话**第一个** qa 节点） | 在第 2 轮上建的分支会挂到第 1 轮下面 → "没挂上" |

### 10.2 修法

`createChildSession` 改走 **`ctx.agents.create({ sessionId: session-<uuid>, meta: { cwd, parentSession, isSeeded:false, delegationDepth:0, agentPreset }, agentOptions, setup })`**（与官方 `sessionController.create` 同一套：`presets.resolve` + `setup: presets.mount`）；挂载点改 `anchorNodeFor()` 按 `parentTurn` 选；`syncTurns()` 让 `turn: null` 的占位节点**认领第一个轮次**；`adoptSession` 改以 `inspect` 为准（刚建、还没落盘也能 adopt）；诊断字段 `sessions` → `agents`。

### 10.3 真机验证方法（隔离 profile，不污染现有数据）

```sh
$env:DSH_HOME = <repo>\artifacts\probe-home
dsh probe --from-default-profile web --dump-config        # 从官方 web 模板建一个临时 profile
dsh plugin --profile probe add "link:<repo>"              # 装本插件（link）
# 把一条真实会话目录复制进 <probe-home>\sessions\…         # 需要"有 2 轮历史"的会话当父会话
dsh --profile probe --port 3081 --no-open
```

| 断言 | 实测结果 |
| --- | --- |
| `POST /branch/diagnostics` | `{agents:true, sessionController:true, agentPresets:true}` |
| `POST /branch/create {parentTurn:2}` | 200；`sessionId=session-ef936c1d-…`（uuid）、`treeId` = 父会话那棵 |
| 子会话落盘 | `sessions/…/session-ef936c1d-…/session.v4.jsonl.zstd` 立刻存在；头里 `parentSession`/`isSeeded:false`/`cwd`/`agentPreset` 全对 |
| `POST /branch/adopt {sessionId:子}` | **同一棵树**、`currentNodeId` = 新节点；磁盘上只有 1 棵树（没有"新根"） |
| `POST /branch/view {sessionId:父}` | `第 2 轮` 的 `children` 含新节点；第 1 轮 `children` 为空 |
| 带首句提问 | `promptDelivered=true`；子会话日志 **11.9KB**（真跑了一轮）；不带提问的只有 **372B**（只有头） |
| **UI 探针**（无头 Edge + CDP，点「＋」→ 填首句 → 提交） | 框数 **3→4**、新连线起点 = 被点的框 `n-2-…`、树 id 未变、新框标题=首句、无报错、地址未变 |

> ⚠️ **两条方法论教训**（都写进这里，避免下一个人重踩）：
> ① **"假环境通过"不等于契约对**：旧假面按我们**以为的**契约实现（`sessions.create` 会落盘、会进 list），
> 于是把缺陷 27 固化了整整一个里程碑。现在假面按**实时 inspection** 建：`agents.create` 造落盘会话、
> `sessions.create` 造**不落盘**会话（把缺陷钉进假环境）。
> ② **`session-<数字>` 这个 id 本身就是红旗**：官方真实会话 id 是 `session-<uuid>`；见到计数器号就该去查
> "这条会话到底有没有落盘"。

### 10.4 缺陷 28：点节点只切到对话末尾，跳不到对应轮次（2026-10-17）

**现象**：在画布上点"第 N 轮"的框 → 主视图切到了那个会话，但**停在对话末尾**（最新一条），
与"点哪个节点看哪一轮"的预期不符。

**根因**：我们只调了 `ctx.uiWorkspace.openSession(sessionId)`。官方这个接口的语义就是"选择会话并显示它的
Conversation"——**没有**"定位到某一轮"的参数（`SessionTarget` 只有 `SessionId | SubagentAddress`），
打开后自然停在最新位置。

**修法**（新增 `src/client/jump-to-turn.ts`）：定位靠对话自己的 DOM 锚点，而不是找官方私有接口：

| 事实（真机 DOM 侦察） | 用法 |
| --- | --- |
| 对话滚动容器是 `[data-conversation-scroll]` | 找锚点的范围 |
| 每轮消息带 `data-chat-turn="<n>"`，用户那条另有 `data-chat-flow-kind="user"` | 挑"这一轮的起点"（优先 user 消息），`scrollIntoView({block:'start'})` |
| 对话是**分页加载**的：很早的轮次一开始不在 DOM 里 | 节点上的 `anchorSeq` → 官方 `ISession.loadThrough(seq)`（经 `ctx.sessions.using()` 借引用、跑完释放）把历史加载到那一轮，再等锚点出现 |
| 刚切会话时 transcript 还没渲染 | 轮询等锚点（默认 3s），**找不到就保持原行为**（停在末尾），不抛、不弹错 |
| 命中后要给人"就是这一轮"的反馈 | 打 `data-dsh-branch-flash`（1.4s 后撤掉）+ 一条 token 化 outline 样式；它同时是**真机门的断言抓手** |

**验证**：

- `jump-to-turn.mjs` 冒烟 **9/9**（假 DOM：挑 user 消息 / 无容器不抛 / 命中调 `scrollIntoView` 并打标记 /
  无锚点 → `turn-missing` / 有锚点先 `loadThrough` 再命中 / `loadThrough` 抛错不冒泡 / 非法轮次 / 无 document）；
- **真机 UI 探针**：会话打开时 `scrollTop=1161`（末尾）、DOM 里只有第 3~4 轮 → 点"第 1 轮" →
  `loadThrough` 把历史拉回（`scrollHeight` 2085 → 5918）→ 高亮落在 `data-chat-turn="1"`、在视野内、`scrollTop=47`；
- **`npm run real-machine` 新增 F-15 全绿**（4 条断言）：定位到被点的轮次、该轮在视野内、
  跳完已切回对话视图、滚动位置离开末尾。

## 12. 缺陷 29：新建的子对话没进父会话的工作区（2026-10-17）

**现象**：在节点上「＋」建出来的子对话，侧边栏里跑到「**未分组**」，不在父对话那个工作区里。

**根因**（官方 `subsystems/workspace.zh.md` 原文）：工作区的成员资格是**账本制**——
"所有权的真源是记录中有序的 `sessionIds`，**绝不从会话 cwd 派生**"，且成员资格要求
「账本里有这个 id」**且**「会话头 cwd 等于工作区路径」两条同时成立。
我们建子会话时只把 `cwd` 传给了 Agent 工厂，**没有任何人调 `attachSession`**，
所以它天生不在任何账本里。

**修法**：

| 位置 | 变化 |
| --- | --- |
| `src/host/session-model.ts` | 新增 `WorkspaceFace` / `WorkspaceRegistryFace` 与 `attachToParentWorkspace()`：`ctx.workspaceRegistry.list()` 按**父会话**反查工作区，再 `attachSession(子会话)`；任何一步失败都**不抛**，返回可读 `reason` |
| `src/host/branch-service.ts` | 建出会话后立刻调用它；失败只记诊断、不拦住建分支；回包新增 `workspaceAttached` / `workspaceId` / `workspaceError`；`summary()` 新增 `workspaces` 能力位 |
| `src/host/routes.ts` / `src/index.ts` / `src/client/capability.ts` | 诊断信封加 `workspaces`；自检区显示「工作区注册表 `ctx.workspaceRegistry`」 |
| `src/client/panel.tsx` | 建会话后的状态行改成 `createdStatus()`：挂上了说「已在父会话的工作区里」，没挂上说清原因并提示会落在「未分组」 |
| `src/testing/fake-sessions.ts` | 新增假工作区注册表（**照账本语义**：只认 `sessionIds` + cwd 校验，不从 cwd 派生），供冒烟驱动真代码 |
| `tools/smoke/branch-m1-cases.mjs` | 新增 3 条：子会话真的进了父会话的工作区（账本断言 + 回包字段）；父会话本身未分组时**照常建成**、回包说清没挂上；部署没有 `workspaceRegistry` 时同样降级不抛错 |
| `tools/smoke/branch-smoke.mjs` | 诊断断言补 `typeof value.workspaces === 'boolean'` |

**验证（真机，共用同一个 `$DSH_HOME`）**：用 `web` profile 起一个新 host（3081）跑**新产物**，
`POST /branch/create`（父会话 `session-826d8f65-…`，父轮次 1）回包：

```json
{"ok":true,"value":{"sessionId":"session-c4976dc5-…","treeId":"t-session-826d8f65-…",
 "nodeId":"n-1-4mj4","promptDelivered":false,
 "workspaceAttached":true,"workspaceId":"4b063222-7fb9-47b7-8645-10fde6f74933"}}
```

`storages/workspace.json` 里该工作区（「f分支对话插件」）的 `sessionIds` **前插了子会话 id**
（10 → 11 条）。验完已清理：删掉测试用的空子会话、把树文档里的占位节点摘掉、从账本里移除该 id
（会话数回到 10），并确认 `workspace.json` 仍可解析、6 个工作区都在。

> ⚠️ 这次真机验证用的是**另起的 host 进程**：正在运行的桌面实例（58823）里跑的还是启动时加载的
> 旧 host 代码（`/branch/diagnostics` 里还没有 `workspaces` 字段），**要重启应用才会用上这次修复**。
> 客户端半不用管——它由 client-modules 热重载。

## 8. 追加用例的约定

1. 新用例优先加进对应里程碑的套件；跨里程碑的纯函数（如导出）**另开一个套件文件**，并在 `package.json` 的 `smoke` 脚本里串上。
2. 每个用例必须有一条"能失败的断言"（例如断言具体错误码、具体字节数、具体顺序），不要只断言"不抛错"。
3. 真机结论必须写清：命令、端口、请求与响应、以及当时是否装了插件。
4. 发现 bug 时同时记录**根因**与**复验方式**；修完把用例补进套件，防止回归。
