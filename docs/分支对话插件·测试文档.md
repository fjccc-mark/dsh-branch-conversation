## 1. 怎么跑

```sh
npm install --legacy-peer-deps         # 官方 SDK 的 peer 声明在 npm 下需要这个开关
npm run typecheck                      # host + client 两个 program
npm run build                          # tsdown（host ESM + client CJS）+ 给 client 套加载器外壳
npm run smoke                          # 四套冒烟，一条命令跑完
```

单套跑法（便于定位）：

```sh
node tools/smoke/branch-smoke.mjs      # M0：存储与路由契约（12 项）
node tools/smoke/branch-m1-cases.mjs   # M1：建子会话 / 节点派生 / 孤儿升根（14 项）
node tools/smoke/branch-m4-cases.mjs   # M4：失败恢复四场景 + 文件节点 + 导出路由（15 项）
node tools/smoke/client-bundle.mjs     # M2：浏览器半产物形状与座位注册（7 项）
node tools/smoke/tree-layout.mjs       # M2：流程图布局纯函数（9 项）
node tools/smoke/export.mjs            # M4：三种导出纯函数（13 项）
```

测试形态说明：本插件**不依赖真机 DSH** 也能覆盖主链路——
`src/testing/fake-sessions.ts` 按官方契约造了一套假会话面（`inspect` 返回 `{meta, events}`、
`list` 带 `parentSessionId`/`origin`、`sessions.create` 不给 seed 时头里 `seedLength = 0`），
用它驱动**真实的** `BranchService`、`TreeStore` 与 `/branch/*` 路由；浏览器半则在一个最小
`window.__ModuleLoader__` + 模块表环境里**真实加载产物**。

## 6. 真机测试记录（M2 收尾，2026-10-15）

### 6.1 环境与方法

- 安装：`dsh plugin --profile web add link:D:\文件\c程序\ai项目开发\f分支对话插件`
  → `web` profile 的 `dsh.profile.bundles` 增加 `dsh-branch-conversation`；`--dump-config` 可见该行（含 `inject: [webServer]`）。
- 启动：`dsh --profile web --port 3080 --no-open`（后台任务），从启动输出取
  `dsh web: http://127.0.0.1:3080/?token=<每进程随机令牌>`。
- 鉴权：`GET /?token=…` → 303 + `Set-Cookie: dsh-auth-<hash>`（签名 cookie，密钥持久化在
  `$DSH_HOME/.credentials.yaml` 的 `client-connection/browser-session` 记录里；`/api/*` 不接受 query token）。
- 探测：带 cookie 发 `GET`/`POST`，并对插件内部状态打临时文件探针（探针已在提交前移除）。

### 6.2 真机抓到的 4 个 bug（均已修）

| # | 真机现象 | 根因 | 修法 | 复验 |
| --- | --- | --- | --- | --- |
| 1 | 启动即失败：`client bundles not found … path: …\lib\client.js` | 官方 client-modules **直接按 `exports["./client"]` 解析产物路径** | 浏览器半产物改到 `lib/client.js`（构建入口 `{ client: 'src/client/index.ts' }`），冒烟与包装脚本同步 | 启动无该错误；产物冒烟 7/7 |
| 2 | 启动即失败：`TypeError: Cannot read properties of undefined (reading 'storageRoot')` | 加载器**不经过 schema** 递入行配置（实测 `config === null`） | `apply` 接 `Partial<Config>`，`withDefaults()` 自行补默认值 | 启动无该错误 |
| 3 | `cannot get property "webServer" without inject`（整条 fiber 挂掉） | loader 读的是 **`entry.options.inject`**（`cordis-plugin-loader` 的 `Inject.resolve(fiber.entry.options.inject, fiber.inject)`），不是模块导出的 `inject` | `cordis.patch.yml` 插入行加 `inject: ['webServer']` | 启动无该错误，`apply` 执行并拿到 `webServer` |
| 4 | 即使注册成功，handler 也拿不到正确请求对象 | webserver 的 handler 签名是 **Node 的 `(req, res)`**，不是 Fetch 的 `Request`/`Response` | 新增 `dispatch()` 适配层：Node 请求 → Fetch `Request` → 路由层 → 写回 `res`，并兼容 Fetch carrier | 适配层就位（尚未取得真机 200，见 6.3） |

### 6.3 ~~未解决~~ **已解决**（2026-10-15 真机轮次二）：插件前缀路由在真机上不可达

> **状态更新**：本节记录的现象已在 **§6.5** 定位到根因（前缀注册缺前导斜杠）并修复；
> 下面"下一步排查方向"里的路线 A/B **都不需要做了**。本节保留原始现象与排除过程，
> 作为"假象有多像真象"的取证记录——注意本节表格里
> `GET /plugins/branch-conversation/client.js → 404` 一行**是我猜的 URL**；
> 真实产物 URL 要从 `__DSH_BOOT__` 里取（见 §6.5.5 W-1.2），那个 URL 本来就是 **200**。

**现象（当时可稳定复现）**

| 请求 | 结果 |
| --- | --- |
| `GET /branch/diagnostics` | **404**（空 body） |
| `POST /branch/diagnostics` | **405**（空 body） |
| `GET /plugins/branch-conversation/client.js` | **404** |
| `GET /api/nonexistent`（官方前缀，对照） | **401 `unauthorized`**（说明官方前缀可达） |
| 桌面实例 `GET /git/status`、`GET /git/config`（已装插件，旁证） | 404（`POST` 为 405） |
| 桌面实例 `GET /zzz-nope`（基线） | 404 |

**已确认的事实链**

1. `apply` 确实执行（探针：`apply called config=null`）。
2. `ctx.inject(['webServer'], cb)` 的回调确实执行，子上下文里 `webServer` 是对象。
3. `register({kind:'prefix', path:'branch', handler})` **成功**：无异常、返回 disposer；
   实例 `port=3080`、`host=127.0.0.1`（与真实监听一致）；直接读实例内部前缀表
   `prefixes.has('branch') === true`，`size` 随注册递增（再加 `zebra` 后为 2）。
4. 但 handler 第一行的探针**零命中** —— 请求没有走到注册的 handler。

**已排除**：服务名错、实例错（port/host/前缀表都对）、路径写法（`branch` 与 `/branch` 都试）、
inject 未生效（子上下文有该服务）、路由被 effect 立即释放（不套 effect 也一样）、
handler 抛错（探针根本没执行）、方法限制（GET 走 404 而非 405）。

**下一步排查方向**

- **首选**：改用官方**可达**的传输——把 `/branch/*` 注册进 connection 的 fetch 注册表
  （官方 `dsh-client-file-upload` 就是往连接层注册一条 `POST` 路由，天然带鉴权与 Host/Origin 围栏）。
- 备选：对比官方 `/api` 前缀与插件前缀在路由表里的存储/派发差异；定位手段是在
  `dsh-host-webserver` 的 `match()` 入口临时加日志（属临时只读实验）。

### 6.5 真机轮次二：路由阻塞点已解决 + 5 个新真机 bug（2026-10-15，按 [测试计划](分支对话插件·测试计划.md) 执行）

#### 6.5.1 结论一句话

**§6.3 的阻塞点找到根因并修复**：插件把 host 路由前缀注册成 `'branch'`，
而 webserver 的前缀匹配要求**带前导斜杠**（`pathname !== prefix && !pathname.startsWith(prefix + '/')`），
于是前缀表里留下一个**永远匹配不上**的键——请求落到 frontend-static 的 fallback
（GET → 裸 404、非 GET → 裸 405），而 `register()` 本身**成功返回 disposer**，形成假象。
修完后 `/branch/*` 全部可达；在放行后的链路上又抓到 4 个只在真机暴露的 bug。

#### 6.5.2 环境与方法

| 项 | 值 |
| --- | --- |

#### 6.5.3 根因取证：前导斜杠对照实验

在探针插件里用**同一条** webServer 注册两种前缀，其余条件完全相同：

| 注册的 `path` | 前缀表里的键 | `ws.match('/x')` | `GET /x` | `GET /x/y` |
| --- | --- | --- | --- | --- |
| `'nolead'`（旧写法，同本插件） | `nolead` | `undefined` | **404**（落到 fallback） | **404** |
| `'/lead'`（正确写法，同官方 client-modules 的 `'/plugins'`） | `/lead` | 命中 | **200** | **200** |

官方 `@deepseek-ai/dsh-host-webserver` 的 `match()`（`lib/index.js:322-332`）：

```js
match(pathname) {
  const exact = this.exact.get(pathname)
  if (exact !== void 0) return exact
  let best
  for (const [prefix, route] of this.prefixes) {
    if (pathname !== prefix && !pathname.startsWith(`${prefix}/`)) continue   // ← 无前导斜杠的键永不命中
    if (best === void 0 || prefix.length > best.path.length) best = route
  }
  return best
}
```

**修法**：`src/core/types.ts` 的 `BRANCH_ROUTE_PREFIX` 改为 `'/branch'`；`cordis.patch.yml` 与冒烟断言同步。
回归用例已进 `branch-smoke.mjs`（断言注册的 `path === '/branch'`）。

## 8. 追加用例的约定

1. 新用例优先加进对应里程碑的套件；跨里程碑的纯函数（如导出）**另开一个套件文件**，并在 `package.json` 的 `smoke` 脚本里串上。
2. 每个用例必须有一条"能失败的断言"（例如断言具体错误码、具体字节数、具体顺序），不要只断言"不抛错"。
3. 真机结论必须写清：命令、端口、请求与响应、以及当时是否装了插件。
4. 发现 bug 时同时记录**根因**与**复验方式**；修完把用例补进套件，防止回归。
