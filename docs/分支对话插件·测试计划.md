## 0. 三个先答的问题

**Q1：已经有 70 项冒烟了，为什么还要测试计划？**
冒烟覆盖的是**纯函数与假会话面**（`TreeStore`、`BranchService`、`layoutTree`、`export`、产物形状）。
它证明不了四件事：① 插件在真实 DSH 组合里**请求能不能打到 handler**；② 面板在真实浏览器/Electron 里**渲染成什么样**；
③ `sessions.create` / `list` / `openWorkspacePath` 在真机上的**行为是否与官方契约一致**；④ 窄屏、键盘、并发标签页这些**人工项**。
本计划只做这四件事，不重复冒烟。

**Q2：网页端和桌面端是什么关系？**
**同一套用例语义，两套运行环境。** 用例编号 `W-*`（网页端）与 `D-*`（桌面端）**逐条对应**：
`W-2.1` 验的是「host 路由在 web profile 里可达」，`D-2.1` 验的是「同一条路由在 Electron 桌面实例里可达」。
差异只允许出现在**环境维度**（见 §1），不允许出现在**期望结果**上——同一编号两端的 `期望` 必须一致，
若不一致，就是缺陷而不是"环境差异"。

**Q3：现在最大的风险是什么？**
快照 §4：插件的前缀路由在真机上**注册成功但不可达**（`/branch/diagnostics` → 404）。
这意味着**所有走 host 路由的用例（≈80%）现在必然失败**，而失败原因不在插件逻辑里——在组合层。
所以本计划的执行顺序把「路由可达性诊断」（W-2.1）放在**功能用例之前作为放行门**，
并给出三条落地路线（§0.3）。**在这个门通过之前，不得把面板不工作记为本插件的功能缺陷。**

### 0.1 环境差异基线

| 维度 | 网页端（web） | 桌面端（desktop） |
| --- | --- | --- |
| 启动方式 | `dsh --profile web --port 3080 --no-open`（CLI，可观测启动日志） | Electron 应用内启动（**不可用 CLI 操作该 profile**） |
| 入口 URL | `http://127.0.0.1:3080/?token=<每进程随机>` | 应用内窗口（当前实测 `127.0.0.1:19387`；端口随实例变化） |
| profile | 自建 `web` profile（可增删插件） | **Electron 独占 `desktop` profile**：CLI 报 `profile "desktop" is managed exclusively by the Electron application` |
| 插件安装通道 | `dsh plugin --profile web add link:<仓库绝对路径>` | **应用内插件管理器**（本机插件 / link 安装） |
| 插件产物落地 | `lib/client.js`（由 `exports["./client"]` 解析，M2 bug #1 的结论） | **同一份 `lib/client.js`**，走同一套 client-modules 解析 |
| host 代码改动生效 | 需**重启**该 profile 进程 | 需**重启应用**（或按插件管理器的重启提示） |
| client 代码改动生效 | 构建后**刷新页面**即可（有 watcher 时 HMR） | 需**重启应用或重新加载窗口**（Electron 侧 HMR 收端未验证） |
| 鉴权 | 启动 URL 里的 token → 303 → 签名 cookie `dsh-auth-<hash>`；`/api/*` **不接受** query token | 应用内已带会话（无手工换 cookie 步骤） |
| 官方对照路由 | `GET /api/nonexistent` → 401（前缀可达的基线） | 同左，但**同时可对照已装第三方插件**（桌面实例上 `/git/*` 实测也是 404） |
| 观察工具 | 浏览器 DevTools（Network / Console / Elements） | Electron DevTools（同样支持 Network / Console） |
| 存储根 | 源码默认 `$DSH_HOME\storages\branch-conversation\v1`（`src/index.ts` 的 `defaultStorageRoot()`，**不使用 `process.cwd()`**；配置项 `storageRoot` 可覆盖）。**实测以 `/branch/diagnostics` 的 `storage.root` 为准** | 与网页端同一台机器、**同一个 `$DSH_HOME`**：两端会**看到同一批树文档**（跨端一致性用例 D-5.4 由此而来） |
| 排障开关 | 插件有配置项 `http`（默认 `true`）：关掉后**只保留存储、不注册路由**，用于隔离"路由问题 vs 存储问题" | 同左 |
| 平台差异风险 | CORS/Origin、SPA fallback 抢先匹配、cookie 作用域 | 模块表解析、侧边栏壳版本、`openWorkspacePath` 落到 Windows 默认程序、窗口尺寸 |

> **本机环境现状（制定计划时实测，非推测）**：`$DSH_HOME=C:\Users\admin\.dsh`；profiles 目录含 `web` / `desktop` / `branch-dev`；
> `web` profile 的 `node_modules/dsh-branch-conversation` 是指向本仓库的符号链接（**插件仍装在该 profile**）；
> 桌面实例 `127.0.0.1:19387` **正在监听**（PID 7112），3080 无监听（上次真机服务已停）；
> `$DSH_HOME/branch-probe.log` 是上次真机探针的遗留物（见 §4.2 环境清理）。

### 0.3 阻塞点的三条路线（先决策，再跑 L2）

测试**不是**"等 bug 修好再测"，而是**先用 W-2.1 把阻塞点钉死，再据结论选路线**。三条路线共用同一套 L3 用例，只有 L2 的期望不同：

| 路线 | 做法 | L2 期望 | 代价 | 备注 |
| --- | --- | --- | --- | --- |
| **A（首选，见快照 §4）** | 把 `/branch/*` 从 webserver 前缀路由改为注册进 **connection 的 fetch 注册表**（官方 `dsh-client-file-upload` 同款：天然带鉴权与 Host/Origin 围栏） | `GET/POST /branch/*` 200，且**未带鉴权时必须被拒**（不是 404） | 需要改造路由注册层；`branch-api.ts` 调用方式基本不变 | 与官方插件同路径，最可能长期可用 |
| **B（保留原来的前缀路由）** | 在 `dsh-host-webserver` 的 `match()` 入口做一次**临时只读实验**（加日志），对比官方 `/api` 前缀与插件前缀在路由表里的存储/派发差异 | 修好后同 A | 需要碰官方包（只读实验，改完全部回滚） | 只有定位到根因才值得选，否则是"绕过" |
| **C（降级为纯浏览器半）** | 放弃 host 路由，树文档落浏览器侧存储 | 无 `/branch/*` 请求 | **推翻已落定的存储独立设计（B2）**，且拿不到 `sessions.create` 血缘能力 | 仅供"网页端支持降为待评估"（裁决 A6）时评估，**不建议** |

**决策规则**：W-2.1 跑完当天必须给出「走 A / 走 B / 申请评估 C」的结论并写入测试文档 §6.3 的续篇，否则后续用例一律记为「阻塞」而不得记为「通过/失败」。

### 0.4 用例格式与优先级

每条的固定格式：`编号` · `优先级` · `前置` · `步骤` · `期望` · `证据`。
*（本文件只写前三项 + 期望 + 证据；实际结果由执行者按 §4.3 模板回填到测试文档。）*

| 级别 | 含义 | 例子 |

**取证纪律（硬性）**：每条用例的证据只认三类之一——**命令与原始响应**、**截图/DOM 片段**、**文件字节比对**。
禁止写"应该通过"；无法取得证据的用例标 `未执行`，并在 §4.4 列出阻塞原因。

**安全护栏（贯穿全部用例）**：

1. **不得改写主对话**：任何用例执行后，主对话的事件条数与最后一条消息必须与执行前逐字一致（W-3.7 专门验）。发现插件写会话日志或改会话头 = **P0 级缺陷**，立即停止后续用例。
2. **不得把凭据写进仓库**：token、`dsh-auth-*` cookie、`.credentials.yaml` 内容一律不出现在提交物、截图可读区域与测试文档里。
3. **产物只认构建**：`lib/` 是构建产物，任何用例不得手改 `lib/`；改动一律回到 `src/` 后重新 `npm run build`。
4. **实验代码必须回滚**：路线 B 的官方包临时探针、任何写盘探针，用例结束即删，并在测试文档记录"曾改动什么、是否已还原"。
5. **不动管理员的桌面实例**（19387）：桌面端用例只做**读取与 UI 操作**；除非管理员在场同意，不重启应用、不卸载插件。

## 5. 风险、假设与不做的事

### 5.1 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 路由不可达仍未解决（快照 §4） | L3 全线阻塞，测试变成"只验 L1/L2" | 本计划把 W-2.1 作为放行门并预置三条路线；路线选定后 L3 用例**无需改写**即可复用 |
| 真机 DSH 版本（`0.2.0-rc.2`）与类型来源（公开 npm `0.0.1-rc.1`/`0.1.2-alpha.2`）不同号 | 类型通过但运行时行为不同，出现"编译过、真机挂" | 每个官方面（`sessions` / `slots` / `uiWorkspace` / `openWorkspacePath`）都**形状探测并降级**；真机用例把"实际字段"写回文档 |
| 桌面端是 Electron 独占 profile | CLI 路线在桌面端完全不可用，容易把"装不上"误判为插件缺陷 | D-1.1 专门把这个负例钉成证据；桌面端安装一律走应用内管理器 |
| 前端下载（Blob）在 Electron 里被拦 | 导出用例在桌面端假失败 | 单独观察 D-6.*；必要时记录为桌面壳限制而非插件缺陷 |
| 测试过程污染环境（探针文件、测试用树文档、坏文档） | 影响管理员日常使用；下一次测试基线不干净 | §0.4 护栏 4、W-10.3 清理并记录；测试用的会话/树单独命名（如 `TEST-` 前缀），便于事后清理 |
| 只读之外的写接口（重命名/移动/删除节点）被误加进 UI | 违反裁决第 3 条 | 用例 **W-1.4 / W-1.3** 显式断言：UI 上**不出现**这些入口；出现即失败 |

### 5.2 假设

1. 网页端可用自建 profile 启动，且**插件已装在 `web` profile**（现状如此）；桌面端安装需管理员在应用内点击。
2. 两端**共用同一个 `$DSH_HOME`**（现状如此）→ 树数据共享，因此 D-5.4a/b 成立；若管理员改为分离的 home，该组用例作废并改写环境基线。
3. 面板渲染与交互可在真实浏览器/Electron 里人工观察（不依赖无头截图——设计文档记录过无头 Chrome 被沙箱拒绝）。
4. 管理员允许：在 `web` profile 上增删插件、临时运行 3080 服务；桌面端只做读取类操作。

### 5.3 本计划**不做**的事（范围外）

1. **不重复** 70 项冒烟的单元/纯函数覆盖（只在 X-4 作为回归门调用）。
2. **不测** 官方 DSH 自身功能（会话列表、模型设置、文件树），只测"本插件是否破坏了它们"（W-1.3、W-1.6）。
3. **不测** v1 明确不开放的能力：重命名/移动/删除节点、拖动改挂、导入 UI、子智能体开分支（设计文档 §3.3、§7）。
