## 2. P0 问题

### F-01 具名导出与 `export default` 混用：`name` / `inject` / `Config` 被 loader 静默丢弃

| 项 | 内容 |
| --- | --- |
| 严重度 | **P0**（插件契约） |
| 置信度 | **已核实**（运行时源码 + 构建产物双侧证据） |
| 位置 | [src/index.ts:46](../src/index.ts#L46)（`export const inject`）、[src/index.ts:56](../src/index.ts#L56)（`export const Config`）、[src/index.ts:252](../src/index.ts#L252)（`export default apply`）；[src/client/index.ts:75](../src/client/index.ts#L75)、[src/client/index.ts:210](../src/client/index.ts#L210) 同款 |

**官方条款**

> Host 插件导出形态（**不要混用**）：`export function apply(ctx, config) {}` + 可选 `export const inject = ['tools']` + `export const Config`；**或者**一个 service class 作为 default export。
> —— `references/official-plugin-dev-skill.md` §3.1

**运行时实际行为（逐行）**

1. loader 拿到模块命名空间后先做"解包"：
   `cordis-plugin-loader/lib/index.js:458` → `const plugin = this.loader.unwrapExports(exports)`
   `…:664-668` → `exports = exports.default ?? exports; if (!exports.__esModule) return exports`
2. 本项目 `lib/index.js` 末行是
   `export { …, apply, apply as default, …, inject, …, name, … }`
   → 有 `.default`，于是 `plugin` = **裸 `apply` 函数**（没有 `.inject`、没有 `.Config`、没有 `.name`）。
3. 这个裸函数交给 Cordis：
   `cordis/lib/index.js:1619-1635`
   `const callback = this.resolve(plugin)` …
   `runtime = { name, callback, …, Config: plugin.Config }`
   `new Fiber(this.ctx, config, Inject.resolve(plugin.inject), runtime, …)`
   → `Config` 是 `undefined`，`Inject.resolve(undefined)` 是空表；`name` 因 `name === 'apply'` 被置为 `undefined`（`…:1625-1626`）。
4. **浏览器侧完全同款**：`dsh-web-frontend/dist/assets/index-5SrrfWpU.js` 里就是同一个 loader（`_init()` → `unwrapExports(n)` → `ctx.registry.plugin(o,…)`）。
5. 参照系：官方客户端产物**只有具名导出**——
   `dsh-client-ui-sidebar-right/lib/client.js` 末尾只有 `exports.apply = apply; exports.inject = inject;`，**没有** `exports.default`。

**后果（逐条都能对上项目现状）**

| # | 后果 | 项目里的表现 |
| --- | --- | --- |
| 1 | `Config` schema 从不生效 → 配置**不校验、默认值不生效** | 于是有了 [withDefaults()](../src/index.ts#L232) 手写补默认值；`cordis.patch.yml` 里写 `config: { storageRoot: 123 }` 会**静默**回落到默认值（与红线"misconfig fail loud"冲突） |
| 2 | `inject` 从不生效 → 所有服务访问都要自己兜 | 于是有了 [serviceOf()](../src/core/types.ts#L41)、`ctx.get()` 兜底、把 `inject` 抄到 patch 行、客户端一整套"形状探测" |
| 3 | `name` 从不生效 | fiber 名退化成匿名；诊断输出只能靠 patch 行的 `id` |
| 4 | 项目的**根因诊断是错的** | `cordis.patch.yml:7-11`、`src/index.ts:41-45`、`src/index.ts:123-127`、[进度快照:60](进度快照.md#L60) 都写着"loader 读的是 `entry.options.inject`，**不是**模块导出的 `inject`"。**真相是两者都会生效**：loader 那一行是把 entry 的 inject **合并进** `fiber.inject`，而 `fiber.inject` 本应由模块导出的 `inject` 填充——是因为 `export default` 把它吃掉了，才显得"只有 patch 行管用" |

**为什么这是"根因级"**：项目在"可选服务缺失"的方向上投入很大（鸭子类型、形状探测、两处 500ms 重试、模块级全局持有、可读降级提示），这些都是**围绕症状**建的。删掉一个 `export default` 就能让 Cordis 自己承担这一切（见 F-08）。

**建议（不实施，只是提案）**

- 二选一，别混用：
  - **推荐**：删掉两处 `export default apply`，保留具名 `apply`/`inject`/`Config`/`name`；
  - 或者把 default 换成对象：`export default { name, inject, Config, apply }`。
- 改完后**重新评估**这些地方（它们的存在理由会消失）：patch 行的 `inject: ['webServer']`（可保留，但不再是"必须"）、`withDefaults()`（可换成让 schema 生效 + 非法配置响亮失败）、`serviceOf()` 的兜底分支、两处轮询（F-08）。
- 验收：重启 profile 后 `dsh --profile web --dump-config` 无 `patch: entry not found`；并用 `cordis_inspect_query` 确认 fiber 的 inject/Config 已挂上（不需要审批）。

### F-02 `/branch/*` 无鉴权、无 Host/Origin 校验：一个"本地可被任意网页触发"的写接口

| 项 | 内容 |
| --- | --- |
| 严重度 | **P0**（安全） |
| 置信度 | 接口存在与无校验 = **已核实**；"任意网页可触发" = **高置信推断**（依据 HTTP 简单请求语义）；危害上限取决于 `openWorkspacePath` 是否限制工作区 = `待实测` |
| 位置 | [src/host/routes.ts:34](../src/host/routes.ts#L34)（整条路由）、[src/index.ts:138-146](../src/index.ts#L138)（注册处） |

**官方给了现成的门**（`docs/subsystems/web-server.zh.md` 与 `dsh-host-webserver` 的类型声明）：

```ts
/** Apply Connection's Host/Origin checks and browser authentication to another Web route. */
requestRejection(request: ConnectionTrustRequest): ConnectionRequestRejection
/** Admit one request: it passes requestRejection and speaks for the operator, or it is refused with that status. */
admit(request: ConnectionTrustRequest): PeerAdmission
```

官方原文还写着：**"其 Connection 插件为每个 Host API route 与 stream 提供 Host/Origin 校验和浏览器会话认证"**、**"载体不拥有认证或 Origin 策略"**。也就是说：**谁注册路由，谁负责调这两扇门**。

**本插件的现状**：`handleBranchRoute()` 从头到尾没有任何鉴权/Origin/Host 判断，直接按 method+path 分派。

**危害面（都是写操作或敏感读）**

| 端点 | 能力 |
| --- | --- |
| `POST /branch/create` | 建新会话（可带首句 prompt，会真的排队投递给 agent） |
| `POST /branch/attach-file` | 把**任意绝对路径**写进树文档（`path` 只做非空检查，不限制在工作区） |
| `POST /branch/open-file` | 把节点记的路径交给**系统默认程序**打开（走官方 `openWorkspacePath`） |
| `POST /branch/split-orphans` / `audit-files` / `set-collapsed` / `adopt` | 改树文档 |
| `GET /branch/export?sessionId=…` | 直接吐出整棵树的 JSON/Markdown（相当于会话结构导出） |
| `GET|POST /branch/diagnostics` | 泄漏存储根绝对路径、能力清单、树数量 |

**为什么"任意网页"够得着**（这是关键，也是可修的点）：

- [readJson()](../src/host/routes.ts#L160) **不检查 `content-type`**；
- 于是 `fetch('http://127.0.0.1:<port>/branch/attach-file', { method:'POST', body: '{"…"}' })` 用默认的 `text/plain` 就是一条**简单请求**——**不触发 CORS 预检**，浏览器会真的把请求发出去（写副作用已经发生；回包读不到，但读回包不是攻击者的目的）；
- 本机 DSH 的默认宿主是 loopback，所以这主要是"用户在自己浏览器里访问了恶意页面"的场景；而 0.2.0-rc.2 的 webserver **允许显式绑定非回环地址**（只有未指定地址 `0.0.0.0`/`::` 在加载期被拒），一旦有人这么做，同网段就能直接调这些端点。

**项目自己的记录**：[进度快照:224](进度快照.md#L224) 把"`/branch/*` 鉴权"列在"未做"里等裁决。**按官方标准，这不该是一个"待裁决的产品选项"，而是插件注册自定义 Web 路由时必须自己接的门。**

**建议（提案）**

1. 在 `register` 时拿到 `ctx.connection`（或 `ctx.get('connection')`），对每个 `/branch/*` 请求先做 `requestRejection(req)` → 非空则按该状态拒；写动作再走 `admit(req)`。
2. `readJson` 校验 `content-type: application/json`（至少对写动作），把"简单请求"这条通道关掉。
3. 收紧 `attach-file`/`open-file`：路径必须落在会话 `cwd`/工作区内（`openWorkspacePath` 是否已限制工作区，请实测；若不限制，这就是本插件唯一的"任意文件交给系统打开"入口）。
4. 若短期不修，至少在 `README`/诊断里明确写"本插件的 `/branch/*` 无鉴权，请勿以 `--host <非回环>` 暴露"，并把它当成已知风险而不是待裁决项。

### F-03 版本门空转 + 开发依赖停在被冻结的 `latest`

| 项 | 内容 |
| --- | --- |
| 位置 | [package.json:43-46](../package.json#L43)（`dsh.engines.dsh`）、[package.json:79-82](../package.json#L79)（peer）、[package.json:85-92](../package.json#L85)（devDeps） |
| 置信度 | **已核实** |

**（1）`dsh.engines.dsh: ">=0.2.0-rc.2"` 零强制。** 官方安装期门禁的实际实现是：

```
dsh-app-boot/lib/index.js:286-301  evaluatePluginCompatibility(manifest, exemptions, runtimeVersion)
  … if (name !== "@deepseek-ai/dsh" && !name.startsWith("@deepseek-ai/dsh-")) continue
```

它**只**遍历 `peerDependencies` 里 `@deepseek-ai/dsh` / `@deepseek-ai/dsh-*` 的条目。本插件的 `peerDependencies` 只有 `@deepseek-ai/cordis` 与 `react`——两个都不匹配这个前缀（`cordis` 不是 `dsh-*`）→ **peers 为空 → 任何宿主版本都放行，且不产生任何警告**。于是 `>=0.2.0-rc.2` 这个"版本门"只写在注释和文档里，实际不设防。

规范做法（官方同一批包一致）：把真正依赖的 dsh 包写进 `peerDependencies`，区间按代切。本项目用了 0.2.0 世代的接口（`sessions.create`、`sessionController.inspect`、`sidebar.panellist`、keyed `main`、slot `locale`），按 `guide/version-matrix.md` §4.2 的下界至少是 `>=0.2.0-0`，上界必须按世代切 `<0.3.0`：

```jsonc
"peerDependencies": {
  "@deepseek-ai/cordis": "~4.0.4",              // 家族规范是 ~4.0.4，不是 ^4.0.4
  "@deepseek-ai/dsh-session": ">=0.2.0-0 <0.3.0",
  // …按实际消费面补
}
```

（提醒：`@deepseek-ai/dsh` 子包的 `latest` 标签**永远停在第一次发布的值**——这也正是下一条问题的成因。）

**（2）devDeps 全落在冻结版上。** 项目 `node_modules` 实际解析到：

```

dsh-client-ui-layout    0.0.1-rc.1
dsh-client-ui-sidebar   0.0.1-rc.1
dsh-client-ui-slots     0.0.1-rc.1
```

而宿主跑的是 `0.2.0-rc.2`（`dsh-client-ui-layout@0.2.0-rc.2` …）。**类型面与被测宿主差一整代**——这正好解释了为什么项目到处写"真机实测才发现签名不对"（webserver handler 签名、slot 选项、服务字段），那些"实测"本质是**用过期类型开发**的必然代价。官方包的 devDeps 是**精确钉运行时版本**的（`dsh-client-ui-deliverables/package.json`：`"@deepseek-ai/dsh-client-ui-renderer": "0.2.0-rc.2"` 等）。

### F-07 样式投递没接平台约定（缺 `data-plugin` / `data-plugin-css`）

| 项 | 内容 |
| --- | --- |
| 位置 | [src/client/style.ts:18](../src/client/style.ts#L18)（`data-dsh-branch-style`）、[tools/build/wrap-client-bundle.mjs:88](../tools/build/wrap-client-bundle.mjs#L88)（`window.__DSH_BRANCH_CSS__`） |
| 置信度 | 平台机制**已核实**；本插件是否被兜住 = **待实测** |

平台侧的真实机制（`dsh-client-modules/lib/client.js`）：

- `:191-194` `removeOwnedStyles(id)`：**按 `style[data-plugin]` 匹配并删除**（模块卸载/HMR 时清理样式）；
- `:489-495` `claimStyles(id)`：`style:not([data-plugin])` 会被**认领**并打上 `data-plugin`，同时用 `data-plugin-css` 记账。

官方产物自己怎么发的（`dsh-client-ui-sidebar-right/lib/client.js:542-546`）：

```js
const tagId = "@deepseek-ai/dsh-client-ui-sidebar-right/ExpandButton.module.css";
if (typeof document !== "undefined" && document.querySelector("style[data-plugin-css=" + JSON.stringify(tagId) + "]") === null) {
  const tag = document.createElement("style");
  tag.dataset.plugin = "@deepseek-ai/dsh-client-ui-sidebar-right";
  tag.dataset.pluginCss = tagId;
  ...
```

**本插件的做法**：把 CSS 塞进全局 `window.__DSH_BRANCH_CSS__`，在 `apply()` 里 `document.head.appendChild(<style data-dsh-branch-style>)`，**没有** `data-plugin` / `data-plugin-css`。

**后果（取决于时序，故标待实测）**：

- 若这枚 `<style>` 存在于 `claimStyles()` 运行窗口内 → 会被自动认领，卸载时能清掉，问题只是"记账名不对"；
- 若 `apply()` 执行晚于 `claimStyles()` → 它既不属于任何 `data-plugin`，也就**不会被 `removeOwnedStyles` 清掉**：HMR/重载会留下重复样式表，而且它挂在 `document.head` 上、没有 effect 兜底。

同时它也踩了官方 §3.2 的两句：**"工厂保持无副作用…样式在 `apply` 里用 `ctx.effect` 注册并返回清理函数"**、**"不要在组件外写 DOM"**。

**建议**：改成平台约定形状——`style.dataset.pluginCss = 'dsh-branch-conversation/panel.css'`、`style.dataset.plugin = 'dsh-branch-conversation'`，幂等判据也用 `style[data-plugin-css=…]`；并把注入动作放进 `ctx.effect(() => { …插入…; return () => el.remove() })`。**另外建议在真机上实测**：卸载/重载插件后 `document.querySelectorAll('style[data-plugin]')` 里有没有残留。

| 项 | 内容 |
| --- | --- |
| 位置 | [src/client/use-main-session.ts:46](../src/client/use-main-session.ts#L46)、[:99-126](../src/client/use-main-session.ts#L99)、[src/client/navigation.ts:20](../src/client/navigation.ts#L20)、[:42-76](../src/client/navigation.ts#L42)、[src/client/index.ts:162](../src/client/index.ts#L162)、[:179](../src/client/index.ts#L179) |

| # | 问题 | 说明 |
| --- | --- | --- |
| 1 | **绕开 storage seam** | 插件数据落在 `$DSH_HOME/storages/branch-conversation/v1`（实测目录存在，8 个树文档 + `_index.json`），不受宿主存储根配置/后端选择影响，也不出现在 storage 检查面里。裁决 B2 要求"存储独立于 DSH"——**可以继续自持**，但应把它当成一次有记录的偏离，并至少复用 Provider（`ctx.storage.domain`）而不是自己再写一遍原子写与锁 |

| 5 | **跨进程无锁** | 锁是进程内的。同一 `DSH_HOME` 上跑两个 host（例如 web + 另一个 profile 同时开着）会互相覆盖；项目文档承认"单点是 host 侧路由"，但没写成已知限制 |
| 6 | **`safeTreeId` 是有损映射** | `treeId.replace(/[^A-Za-z0-9._-]/g,'_')`：两个只差非法字符的 id 会映射到**同一个文件**；`listTreeIds()` 返回的是替换后的名字，读回来的 `treeId` 可能与调用方持有的不一致。会话 id 是 UUID，现实风险低，但这是"静默合并两棵树"的隐患 |
| 7 | **结构校验偏弱** | `isTreeDocument()` 只查 `schema/treeId/root.sessionId/nodes[].{id,sessionId,kind,children}`；`turn`/`collapsed`/`file.path` 等字段坏了照样通过 |
